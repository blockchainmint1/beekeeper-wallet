## 2. Internal documents (blocking item 2)
`scripts/make-public-copy.sh` copies tracked files only and leaves out `.env`, `.lovable/`, everything in `docs/` except `docs/images/`, `roadmap.md`, `AGENTS.md`, `SECURITY-AUDIT.md` and any `*audit*` file. If anything private is still in the output, the script exits with an error. In the first copy (389 files), gitleaks reported only the storage-key-name false positives. The README no longer links private docs or lists open items. Its Lovable sync notice is removed from the public copy.

## 3. §3: a status lookup could claim a customer ID (fixed)
- `ownerDecision(existing, address, action)` returns `unclaimed` for a `lookup` on an unowned ID. `vectorPayLinkStatus` never writes to the owner table. For an unclaimed ID it returns `linked` and `needsConfirm: true` with no bank details and no first name. The cash-out screen then clears the local link record and asks for a fresh dashboard code.
- **We also fixed a related issue that was not in the report.** Before this change, `redeemVectorPayLink` claimed ownership *before* calling VectorPay, so any made-up code could claim an ID. The claim now happens only when `mayClaimAfterRedeem` holds, meaning VectorPay answered `ok && linked`. It goes through `claimAccountOwner` (an `ignoreDuplicates` upsert, then a re-read, failing closed).
- A wallet that already owns its ID behaves as before. A wallet with an unclaimed ID re-links once. Today 2 IDs are claimed.
- Not verified: how VectorPay responds when the same account redeems a second code for an `account_ref` it already has linked. We assume it accepts.
- Tests: `src/lib/cashout/account-owner.test.ts` (5 cases).
